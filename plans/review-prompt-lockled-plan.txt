In short: a keyboard (SN32F2xx Cortex-M0, QMK) talks Bluetooth through a closed CH582F module. The only host-to-board path over the air is the keyboard LED output report (one byte: Num, Caps, Scroll, Compose, Kana, 3 padding bits), which the module forwards to the board as a UART frame. A Mac can write it raw, one acknowledged write per ~30 ms (~32/s; writes issued at once complete no faster). The goal is now-playing text (~30 characters) and clock sync without the cable. Caps Lock belongs to the user and must never be written. The draft: change coding over four data lights (15 masks, ~3.9 bits per write) with base-15 packing, sync/header/CRC-16 framing, no duplicate frames, resend later; plain 16-value nibbles plus Reed-Solomon over GF(16) with timing-derived erasures if the tests allow.

What I want from you:
1. **Better schemes.** Go hog wild, then be honest about each: anything that beats ~3.9-4 bits per write at ~32 writes/s, or makes the same rate more robust or simpler. Consider, among whatever else you think of: using write timing as extra information (inter-write delay modulation, given ~30 ms writes with jitter); async/pipelined writes; the plain-value alphabet versus change coding; whether Caps can be used safely at all (e.g. only as a transient that the decoder and the Mac's own Caps state can never confuse; the owner's view is that Caps must keep working normally); text compression (a small alphabet, the LCD's font is limited, base-95, dictionary/delta of the previous title, sending only the changed part); clock-specific encodings (send only a correction; use the frame's own timing); framing and sync that a human pressing lock keys, another keyboard, or the Mac's Caps rewrite can never imitate; whether the 2.4G dongle path is faster (quill4gen7: 8-40 ms a bit there); and any back channel the board might have for acknowledgements (its frames to the module are keyboard, consumer and profile reports; the BLE descriptor also has a mouse, a system-control collection, a 120-key bitmap, an eject plus vendor bit, and a Surface Dial collection: could an input report the OS ignores carry an ack that the host reads with Input Monitoring, and what would it risk?).
2. **Error handling.** Is "CRC-16, no duplicates, resend later" right for this channel, or would a code (Reed-Solomon, a convolutional or deletion-correcting code such as VT/marker codes, fountain codes, interleaving) earn its cost, given that Bluetooth's link layer already retransmits and the likely errors are lost or merged frames (deletions) and interfering reports (insertions)?
