No blocking issue found in this change for the intended serial bench use. The host reply validation should be tightened, and the existing USB transport has a possible stall beyond 25 ms.

1. **Note — buffer access is safe on the actual dispatcher; `length < 5` is not a complete reply-size guard.**

   ChibiOS allocates `buffer[RAW_EPSIZE]`, where `RAW_EPSIZE == 32`, and calls the handler with `sizeof(buffer)` only after receiving the requested size. VIA forwards that same buffer and length, then echoes it. The non-VIA path also echoes the same buffer. Thus every reachable read and write for ops 4–6 fits: request through `data[4]`, response through `data[8]`. See [usb_descriptor.h:289](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/tmk_core/protocol/usb_descriptor.h:289), [usb_main.c:517](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/tmk_core/protocol/chibios/usb_main.c:517), [usb_driver.c:337](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/tmk_core/protocol/chibios/usb_driver.c:337), [via.c:280](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/quantum/via.c:280), [via.c:481](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/quantum/via.c:481), and [hid_protocol.c:974](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/hid_protocol.c:974).

   The guard covers the input argument for ops 4/5 but would permit an out-of-bounds reply with a genuinely 5–8-byte buffer. Op 6 needs no argument but still needs nine bytes for its reply. Defensive hardening would require `length >= 9` for these ops—or 32 for the shared devhook case, whose existing probe writes through byte 31. This is currently unreachable through this board’s dispatcher. [hid_protocol.c:543](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/hid_protocol.c:543), [hid_protocol.c:853](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/hid_protocol.c:853).

2. **Note — no accidental persistence; later brightness keys deliberately adopt the temporary level.**

   Op 4 changes only `bkl_level`; op 5 changes only `display_powered` and the GPIO. Neither updates `kb_config` nor marks it dirty. Deferred writes serialize the separate `kb_config` object, without sampling live brightness. Therefore a pending write, battery FULL save, clock-mode change, BT-slot change, or RTC-period save cannot capture the host’s temporary LCD level. Power state has no persisted field. [display.c:252](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:252), [display.c:283](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:283), [kb_eeconfig.c:25](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/kb_eeconfig.c:25), [kb_eeconfig.c:48](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/kb_eeconfig.c:48), [kb_eeconfig.c:67](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/kb_eeconfig.c:67), [kb_eeconfig.c:107](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/kb_eeconfig.c:107), [battery.c:508](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/battery.c:508).

   The other whole-block write is the explicit `WDT_TEST_HOOKS` test operation; it writes its own invalid pattern, not live brightness. The bootloader splash uses the same nonpersisting setters. Boot restores the saved brightness and starts powered on. [kb_eeconfig.c:133](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/kb_eeconfig.c:133), [display.c:1151](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:1151), [display.c:294](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:294).

   Fn+PgUp/PgDn subsequently adjusts the **current temporary level** and schedules that resulting level for persistence—even when already at a limit. For example, host level 20 followed by PgDn saves 19 after settling. That is acceptable for intentional key adjustment and the unattended bench premise, but reboot restoration is no longer guaranteed after such a gesture. [ak820pro.c:363](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/ak820pro.c:363), [display.c:273](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:273).

   Also, the reply’s “saved” value comes from the RAM configuration cache: during the five-second settle window it can describe a pending value rather than already-programmed flash. [kb_eeconfig.c:40](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/kb_eeconfig.c:40), [kb_eeconfig.c:84](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/kb_eeconfig.c:84).

3. **Note — no torn state or stuck-off race found.**

   The shared state is volatile byte-sized data; the archived ELF confirms `STRB`/`LDRB` accesses. Main-loop writers cannot run midway through the ISR. GPIO writes use dedicated `BSET`/`BCLR` registers rather than a port read-modify-write. Off stores `display_powered = false` before clearing the pin, and subsequent ticks also clear it: an interrupt cannot leave it permanently high. [display.c:133](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:133), [display.c:212](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:212), [display.c:223](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:223), [hal_pal_lld.h:330](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/lib/chibios-contrib/os/hal/ports/SN32/LLD/SN32F2xx/GPIO/hal_pal_lld.h:330).

   One existing transient: turning on writes high based on the uncapped level, ignoring PWM phase and cap until the next serviced tick—nominally 50 µs. Brightness changes likewise take effect at the next tick. The response describes the configured effective level, not instantaneous pin voltage. [display.c:267](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:267), [display.c:283](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:283).

4. **Should fix — the existing reply transport does not guarantee the 25 ms budget.**

   The new handlers themselves perform only bounded RAM access and, for op 5, a GPIO write: no LCD drawing, deferred drawing request, wait, or lock. The LCD overlay is explicitly pushed by key paths; it does not poll brightness. [hid_protocol.c:860](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/hid_protocol.c:860), [param_overlay.c:54](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/param_overlay.c:54), [param_overlay.c:191](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/param_overlay.c:191).

   However, sending the reply reaches `send_report(... TIME_MS2I(100) ...)`, then a queue write that can wait for space and takes OS locks. A congested/non-draining IN endpoint can therefore stall the main loop beyond 25 ms. This predates the change and should not normally arise with this script’s one-request/one-reply flow, but the complete path is not strictly nonblocking. [usb_main.c:509](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/tmk_core/protocol/chibios/usb_main.c:509), [usb_main.c:392](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/tmk_core/protocol/chibios/usb_main.c:392), [usb_driver.c:253](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/tmk_core/protocol/chibios/usb_driver.c:253), [hal_buffers.c:728](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/lib/chibios/os/hal/src/hal_buffers.c:728).

6. **Should fix — host replies need length and op validation. Argument validation also needs cleanup.**

   The existing `xfer()` correctly checks channel `0x13`, command `0x76`, and `SET_VALUE`; an unhandled response is rejected. It does **not** check report length or echoed `r[3] == op`. In a mocked run, an op-2 probe reply was accepted and printed as LCD state; a short report raised `IndexError`. Require a full report and matching op before decoding. [devhook.py:22](/Users/jdlien/code/ak820-pro/scripts/devhook.py:22).

   The request framing is correct: report ID plus 32 bytes. The printed field order and saved-minus-one decoding exactly match firmware `[level, max, on, effective, saved+1]`. Extra arguments are silently ignored, missing commands raise `IndexError`, and unknown commands exit successfully without action. Validate command/arity before opening the device, and either enforce the advertised range or document clamping. 7. **Note — several existing behaviors matter for the current map.**

   - **PWM is nonlinear:** duty is `bkl_duty[effective] / 48`, with a 20 kHz tick and approximately 416.7 Hz PWM. Level 5 is 5/48 duty; level 23 is continuously high. Average over many 2.4 ms periods and exclude transitions. Some header/config comments describe older behavior; use the actual table and dedicated timer. [display.c:201](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:201), [indicators.c:111](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/indicators.c:111).
   - **Caps are honestly reported:** effective is `min(level, cap)`, or zero when off. The idle ladder is disabled in this build; low-battery lights-cut affects RGB only. If enabled later, the ladder can cap LCD brightness at 4 or 0. [power.c:52](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/power.c:52), [power.c:84](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/power.c:84).
   - **RGB stepping does draw:** VIA RGB changes are polled by the parameter overlay. Allow its two-second hold and restoration drawing to finish before sampling. LCD ops do not trigger it. [param_overlay.c:196](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/param_overlay.c:196), [config.h:420](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/config.h:420), [display.c:2274](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/graphics/display.c:2274).

The battery log records effective brightness at the interval’s end, not its average over a sweep.
