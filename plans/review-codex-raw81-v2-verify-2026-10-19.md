1. **Wrap accounting is correct, with a conditional latency bound.** Both writers update `r81_long` and `r81_long_last` under the kernel lock; there is no ISR/thread lost-update or double-count race. [`ch582f_ajazz.c:689`](C:/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/bluetooth/ch582f_ajazz.c:689)

   The exact requirement is **less than 65,536 running-counter ticks between extension samples**, or **349.525 ms**. Scheduling every 32,768 ticks provides approximately **174.763 ms of additional latency margin**, including callback execution/rearming delay. A lock spanning the numerical wrap boundary is harmless within that limit. Ordinary callback lateness does not accumulate clock drift: the code adds actual counter deltas.

   This is not an unconditional bound against interrupt starvation. If neither path samples for a full wrap, [`chTimeDiffX():461`](C:/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/lib/chibios/os/rt/include/chtime.h:461) still loses whole wraps. The deficit is a multiple of 65,536 ticks and can accumulate; it is **not bounded to one wrap**. With an uninterrupted counter, arithmetic errors remain under-counts, modulo the intentional 32-bit rollover. Elapsed comparisons require ages below that rollover period, approximately **6.36 hours**. This preserves QMK’s existing timer assumptions rather than providing a clock independent of interrupt service.
