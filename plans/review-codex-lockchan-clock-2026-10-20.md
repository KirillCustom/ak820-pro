1. **Must-fix — Invalidate the legacy trim window across host corrections.**  
   The trim compares `rtc_seconds_count` with PCF absolute time, explicitly assuming that reference was not rewritten. Neither clock setter invalidates `rtc_cal_valid`. Wireless sync makes that assumption false while `PCF_LEGACY` remains active.

   For example, a +1-hour correction across a 600-second window produces `ticks=600`, `real=4200`; with nominal period 33600, the existing half-step calculation proposes **19200**. Smaller discontinuities can also produce persistable bad calibration. A backward jump can stall the window until calendar time catches up.

   Invalidate on accepted external corrections and PCF rewriting; reopen only after the slew/reload and PCF transaction have settled. Ordinary legacy phase snaps should retain their existing snap-immune behavior. `bias=0x7FFF` alone does not isolate this learner. 2. **Must-fix — `RETRY` must not announce a successful host synchronization.**  
   `rtc_set_time_ms()` increments `host_sync_gen` **before** checking `rtc_now()`, and before later rejection paths. During wake recovery, an attempted wireless set can therefore make `wake_coarse()` yield to a “new host time” that was never applied. If retries expire, the slow counted-sleep clock can remain authoritative; a previously true `host_synced` can also suppress acquisition.

   Advance the generation only when the correction is accepted. Rejected and retriable attempts must leave synchronization ownership unchanged.    Failure/recovery paths clear `pcf_pending`. Once the machine becomes idle, the legacy guard permits discipline again—even though the PCF may still contain the pre-sync calendar. 7. **Must-fix — DST, time-zone changes, and wall-clock steps need explicit invalidation/rescheduling.**  
   Reusing USB’s conversion correctly obtains local fields at an instant. It does not make local civil time advance continuously through an offset change.
